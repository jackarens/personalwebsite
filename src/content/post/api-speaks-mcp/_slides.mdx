## What MCP is, quickly

<ul>
	<Fragment as="li">Model Context Protocol. Open spec, Anthropic published it Nov 2024. OpenAI, Google, Cursor, Salesforce, Stripe all adopted it.</Fragment>
	<Fragment as="li">JSON-RPC. Runs over stdio locally or HTTP remotely.</Fragment>
	<Fragment as="li">Client (Claude Desktop, Cursor) connects to your server and asks what it offers.</Fragment>
	<Fragment as="li">Model decides what to call. Client runs the call, hands the result back.</Fragment>
</ul>

## Most tools look like this

```ts
defineProjectTool(token, db, {
```

## One schema, three consumers

<div class="starred">

```ts
// libs/shared/server-utils/…/schemas/project.schema.ts
export const ApplyTemplateBodySchema = Type.Object({
  confirm: Type.Optional(
    Type.Boolean({
      description: 'Set to true to confirm re-applying a template…',
    }),
  ),
  templateId: Type.String({ description: 'ID of the template to apply' }),

// apps/api: the REST route validates with it, and it lands in openapi.json
fastify.post('/projects/:projectId/apply-template', {
  schema: { body: ApplyTemplateBodySchema, operationId: 'applyTemplateToProject' },
}, handler);

// apps/mcp: the tool advertises the same object as its inputSchema
inputSchema: Type.Object({ projectId, body: ApplyTemplateBodySchema }),
```

<aside class="notes">
- TypeBox builds plain JSON Schema objects with TypeScript types attached.
- One definition: Fastify validates requests with it, the OpenAPI generator documents it, and the MCP tool hands it to the model.
- Change a field and all three move together. No drift between docs, API and tool.
- Route excerpt trimmed; the real one also declares params, responses and auth.
</aside>
</Slide>

## Things to check on Monday

<ol style="font-size:0.9em">
	<Fragment as="li"><strong>Is each type defined once, as JSON Schema?</strong> Zod, Pydantic, TypeBox and OpenAPI</Fragment>
	<Fragment as="li">Do its fields carry descriptions, enums and examples?</Fragment>
	<Fragment as="li">Can a new caller discover what exists in one call?</Fragment>
	<Fragment as="li">Are writes plain objects or nested/deep unions?</Fragment>
	<Fragment as="li">Do errors name the field and the fix, so callers can retry?</Fragment>
	<Fragment as="li">Where do your production docs live? Can MCP resources serve that same source, or are you porting a copy that will drift?</Fragment>
</ol>

<aside class="notes">
- The big one first: if your types already live in one JSON Schema definition, the MCP tool definition is mostly done. Same object validates requests, documents the API and tells the model what to send (the "one schema, three consumers" slide).
- Descriptions are the prompt. A field called "type" with no description is a coin flip.
- Discovery: one call that returns the shape of the account or workspace saves the agent twenty list calls.
- Plain objects over nested oneOf/anyOf: models handle flat bodies far better.
- Errors: name the field and the problem. The agent retries; a bare 400 ends the conversation.
- Docs: if they live in a CMS or a help centre, an MCP resource either fetches them from there or you end up with a second copy. Copies drift. Ours: the API reference is generated from openapi.json, and the agent guides are markdown in the repo, served as MCP resources.
- While you're in there: "configure this in the app" tells an agent the API can't, even when it can.
</aside>
